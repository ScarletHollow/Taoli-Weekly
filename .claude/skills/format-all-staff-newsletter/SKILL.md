# format-all-staff-newsletter — 全员版 Newsletter 排版 Skill

## 一、用途

本 Skill 是**生成类**(注册表编号 G-03),把一期周报的「期元信息 + 各条目集」聚合、排版为一份**完整、可直接进入人工审核的全员版 newsletter markdown 草稿**。

- **产出去向**:`weekly-report/drafts/YYYY-WW-draft.md`(D 执行手册节点 2 的产出;写入前对既有同名文件做 `.bak` 备份)。
- **输入前提**:期元信息 + 期要点(来自 80+「本周必看」条目)+ 业务层条目集 + 技术层条目集 + 桃李建议,均为本 Skill 的上游(采集/评分/写作 Skill)已产出的**准成品**。本 Skill **只负责按 C 分册骨架排版**,不重写各条目的内容与事实。
- **不做什么(红线)**:
  - **不做去重**:同类/跨期去重归 D 分册 **D5 步骤**(AI 读 `dedup_key` 做事件级去重),本 Skill 不实现、不调用去重逻辑;
  - **不自动发布**:发布归 D 分册**节点 4 人工操作**。本 Skill 只生成**草稿**,绝不执行发布动作、绝不把任何信号 `report_status` 置为 `published`;
  - **不评分**:分数由 `score-taoli-relevance` 初评、人工终审修正,评分**不直接进正文**。

## 二、输入 schema

调用本 Skill 前,以下输入必须齐备(缺失即提示上游补齐):

```jsonc
{
  "period": {                         // 期元信息(C 分册 1.1)
    "issue": "2026-W32",              // 期号,ISO 周编号 YYYY-WW
    "publish_date": "2026-08-10",     // 发布日(周一中午或下午)
    "count": 6,                       // 本期条数 = 业务 + 技术 + 政策加急
    "count_breakdown": {              // 条数构成(建议填写)
      "business": 4, "tech": 2, "policy": 0

    "data_window": "2026-08-03 — 2026-08-07", // 数据窗口(采集起止日期)
    "reviewer": "",                   // 审核人(留空待人工署名)
    "publisher": ""                   // 发布人(留空待人工署名;由人填写)
  },
  "headline": "……",                   // 期要点,≤60 字,必须出自 80+「本周必看」条目
  "business_entries": [               // 业务层条目集(3-5 条,每条一个对象)
    {
      "id": "C-B01",                  // 编号,本期唯一
      "title": "……≤30 字",            // 标题:谁 + 做了什么 + 对谁有用
      "summary": "……≤40 字",          // 一句话要点
      "entity": "公司 / 品牌 / 产品",
      "education_scenario": "……",     // 教育场景(对齐 A 分册 education_scenario)
      "workflow_change": "原流程 → AI 介入后流程", // 对齐主文档「企业 AI 工作流拆解模板」
      "data_loop": "是/否:……",        // 数据闭环说明
      "source_level": "S|A|B|C",      // 每条核心事实须 ≥1 个 S 级来源
      "sources": [{"label":"来源 1","url":"https://…","level":"S"}, "…"],
      "taoli_meaning": "……",          // 桃李含义(可直接借鉴/需自行研发/可购买第三方/暂不值得投入)
      "body": "……2-3 段正文",          // 首段给结论;含工作流变化/数据闭环/行业含义

      "level": "本周必看"
    }
  ],
  "tech_entries": [                   // 技术层条目集(2-3 条,每条一个对象)
    {
      "id": "C-T01",
      "title": "……≤30 字",
      "model": "模型/平台名",
      "capability": "文档与视觉 / Agent 与工作流 / 生产应用 三类能力的新变化",
      "edu_use": "该能力可用于教育的具体用途",
      "edu_implications": "对教育意味着什么(必填,缺失不允许定稿)",
      "taoli_impact": "对桃李选型/产品路线的影响",
      "source_level": "S|A|B|C",
      "sources": [{"label":"来源 1","url":"https://…","level":"S"}, "…"],
      "body": "……150-300 字正文",
      "score": 72,
      "level": "重点关注"
    }
  ],
  "taoli_actions": [                  // 桃李可执行建议(2-4 条,每条一个对象;字段与 write-taoli-actions 输出对齐)

      "action_id": "AC-01",
      "suggestion": "动词开头的可执行建议(一句话,≤50 字)",
      "reason": "支撑论据(可回溯到来源条目编号)",
      "owner_team": "负责团队(桃李内部)",
      "priority": "高|中|低",

    }

```

> 条目对象的字段由上游 Skill(`write-company-analysis`、`write-taoli-actions`)产出,并与 **A 分册信号 JSON** 字段对齐(`education_scenario` / `workflow_stage` / `ai_capabilities` / `source_level` / `target_users` / `scoring` 等)。本 Skill 只做排版与语言规范的统一处理,不新增事实。

## 三、输出 schema

**输出**:一份完整 newsletter markdown(草稿),结构**固定 6 区、顺序不可调换**:

```text
① 期元信息(表头,非正文区块)
② 期要点(≤60 字)
③ 业务层正文(3-5 条)
④ 技术层正文(2-3 条)
⑤ 桃李可执行建议(2-4 条,四类分级)
⑥ 附注(来源与存疑)
```

文件落位:`weekly-report/drafts/YYYY-WW-draft.md`。

输出文件的**骨架模板**(排版基准):

## 四、执行步骤

1. **核对输入完整**:确认 `period`、`headline`、`business_entries`、`tech_entries`、`taoli_actions` 五块齐备;缺失即提示上游补齐,不自行编造。
2. **校验条数与区间**:
   - 全篇条数 `5 ≤ N ≤ 8`(业务层 3-5 + 技术层 2-3,重大政策可追加 1 条政策加急);
   - 超过 8 条或低于 5 条,退回上游增删后再排,宁缺毋滥、不硬凑;
   - 建议区 `2-4` 条,超限退回。
3. **校验期要点**:≤60 字,且**必须出自 80+「本周必看」条目**;发现期要点由 65-79 分条目提炼时,退回重写。
4. **校验分层归属**:业务类条目进业务层,模型/平台能力类条目进技术层;分错层退回重归。
5. **按 6 区骨架组装**(顺序固定):期元信息表头 → 期要点 → 业务层 → 技术层 → 桃李建议 → 附注。
6. **统一可读性处理(排版时一次性执行,不单独建检查 Skill)**:
   - 全文以「桃李」称呼公司;句子 ≤40 字;
   - 首句结论规则:每条正文第一句直接给结论,禁止「近日、据悉、据媒体」等铺垫开头;
   - 术语替换:Agent→AI 智能体、多模态→能读图能听音、OCR→文字识别、工作流→做事流程、数据闭环→AI 结果反哺下一轮教学、上下文长度→一次能读入的信息量、私有化部署→数据装在自己服务器上;首次出现的生僻词给一句括号解释;不堆叠英文缩写;
   - 建议区每条落定四类分级之一,不得模糊。
7. **标注来源与存疑**:正文每条带来源标注(S 级优先);存疑点集中写入附注区。
8. **自检(check-source-quality 移交前)**:复核「每条核心事实 ≥1 个 S 级来源」是否可从 `sources` 追溯;期要点/标题/条要点字数是否达标。
9. **落文件**:写入 `weekly-report/drafts/YYYY-WW-draft.md`(写入前 `cp` 既有文件为 `.bak`);**不触碰 `signals/` 与 `published/`**。产出后可移交 `check-source-quality` 做来源质量检查,再交 D 执行手册节点 3 人工审核。

## 五、写作规范

1. **首句给结论**:每条正文第一句 = 谁 + 做了什么 + 核心影响;先结论后展开。
2. **面向全员语言**:读者含非技术同事;术语按替换表处理,不堆英文缩写,句子 ≤40 字。
3. **层级表述**:业务层偏「产品与业务变化」,技术层偏「模型/平台能力及其教育影响」,两层的「对教育意味着什么/桃李含义」必填不省。
4. **条数宁缺毋滥**:不凑数、不硬塞低质量条目;类目比例(50% 教育 / 25% 模型 / 15% 政策 / 10% 海外)内分配,某类无重要内容可少于比例。
5. **建议只源于本期条目**:桃李建议只写本期业务层/技术层条目能支撑的,不凭空新增;每条含建议/理由/负责团队/优先级/验证方式/来源条目编号六要素,并落定四类分级之一。
6. **来源如实标注**:S 级优先;企业自述(S)与实际案例(A)分开表述,不得混写;B/C 级线索与未核实数字进附注,不伪装成已核实事实。
7. **不越权**:草稿不做去重决策、不改变条目事实、不进行任何发布动作;分数可内部参考但不进正文。
