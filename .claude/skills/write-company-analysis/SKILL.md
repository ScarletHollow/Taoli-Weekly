# 企业分析段撰写(write-company-analysis)

## 一、用途

把**单一企业 + 本期 selected 信号**转换成 newsletter **业务层分析段条目**,即 C 周报输出规范第三章定义的字段完整的单条内容。本 Skill 是生成类 Skill(G-01),只消费**已进入生成池的 selected 信号**(状态见 A 信号数据手册;report_status 必须为 selected,frozen/published 不再改写)。

- 前置:信号已完成采集、去重(D 分册 D5)、分类、评分(A-02/E 锚点)与来源核查(A-03),以 A 分册信号 JSON 为准输入。
- 后置:产出的条目进入 C 模板业务层区,由 format-all-staff-newsletter 组装整份 newsletter。
- **本 Skill 不负责去重**(归 D 分册 D5)与**发布**(归 D 分册节点 4 人工操作)。指令内不包含任何自动发布动作;report_status 的 published 由人工在节点 4 置位。

## 二、输入 schema

本 Skill 一次只处理**一家企业**的**一条 selected 信号**(多条信号需逐条调用)。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| signal_id | string | 是 | 信号 ID,`SIG-YYYY-WW-序号`;进入输出作为溯源 |
| company / brand / product | string | 是 | 公司 / 品牌 / 产品名(输出「企业/产品」) |
| title | string | 是 | 信号标题(≤40 字),仅供撰写参考,不等于条目标题 |
| published_at | string | 是 | 信息来源对外发布日期(YYYY-MM-DD),与 A 分册对齐 |
| event_at | string | 是 | 事件实际发生时间(YYYY-MM-DD);正文首段「何时」取自 event_at,缺省时退化为 week 对应「本周」,避免臆造日期 |
| education_scenario | string | 是 | AI 进入的教育场景(个性化学习 / 作业批改 / 课堂授课 / 教研备课 / 学情诊断等) |
| workflow_stage | array\<string\> | 是 | 被 AI 介入的业务流阶段(对齐主文档「企业 AI 工作流拆解模板」) |
| ai_capabilities | array\<string\> | 是 | AI 能力(OCR / 多模态理解 / 知识库 / 推荐 / Agent / 内容生成 / 诊断 / 规划) |
| new_change | string | 是 | 本次新变化:相对上一次观察具体改变了什么 |
| target_users | array\<string\> | 是 | 服务对象(教师 / 学生 / 家长 / 教务运营 / 学校) |
| source_url | array\<string\> | 是(≥1) | 全部来源 URL;写作时按证据引用,不得臆造 |
| source_level | enum(S/A/B/C) | 是 | 该信号最高来源级别;核心事实须有 S 级 |
| evidence | array\<object\> | 是 | 核心事实证据,每项 `{fact, source_level, source_url}` |
| verification | object\|null | 否 | 来源核查结论(`{source_level, checked_url, conclusion, note}`) |
| limitations | array\<object\> | 否 | 已知局限(`{aspect, note}`);存疑点要如实进正文/附注 |
| scoring | object | 是 | 六维评分 + 总分 + 等级 + 理由;总分决定条目位置(见下) |
| report_status | enum | 是 | 必须为 `selected`;其余状态不进入写作 |
| reviewer_feedback | string | 否 | 人工审核意见;**存在时优先遵循**(人已修正的事实与口径) |
| special_override | object\|null | 否 | 人工强制进入标记;非 null 时在正文标注「人工强制进入」及理由 |

> 输入完整性由 check-source-quality 把关:每条核心事实 ≥1 个 S 级来源、source_level/source_url 完整,缺失时退回补充后再写作。

## 三、输出 schema

输出**一条业务层条目**(编号 C-B01 起),按 C 周报输出规范第三章字段清单:

| 字段 | 要求 |
|---|---|
| 编号 | 本期唯一,如 C-B01 / C-B02(由 format-all-staff-newsletter 统一编号,本 Skill 可先占位) |
| 标题 | ≤30 字,直陈「谁 + 做了什么 + 对谁有用」,不用修辞与感叹号 |
| 一句话要点 | ≤40 字,一句话说清核心事实 |
| 企业/产品 | 公司 + 品牌 + 产品 |
| 教育场景 | 来自输入 education_scenario |
| 工作流变化 | 原流程 → AI 介入后流程(对齐「企业 AI 工作流拆解模板」) |
| 数据闭环 | 是否形成「AI 输出反哺下一轮教学」的闭环:是 / 否 + 一句说明 |
| 来源等级 | S/A/B/C;核心事实标出 S 级来源 |
| 桃李含义 | 对桃李业务的具体意义,1-2 句 |
| 借鉴分级 | 四类措辞之一:可直接借鉴 / 需自行研发 / 可购买第三方 / 暂不值得投入 |

正文(2-3 段,200-400 字,不含桃李含义段):
- 首段:核心事实(谁 + 何时 + 做了什么 + 服务谁)。
- 中段:工作流变化 + 数据闭环(原流程 → 新流程)。
- 末段:行业 / 竞争含义,以及局限或存疑点。

**可交付为 markdown 或结构化对象**,由 format-all-staff-newsletter 消费。最终正文字句不得直接照抄评分与判档理由(scoring 数值不进正文)。

## 四、执行步骤

1. **校验输入**:确认信号 `report_status == "selected"`;确认有 S 级证据支撑核心事实(无则退回 verify-source-evidence 核查,不得带病写作);读取 reviewer_feedback,若有人工修正口径则以人工口径为准。
2. **定位条目位置**:看 scoring.total — 80+ 进正文主位(期要点开首 + 业务层主位);65-79 进正文;50-64 一般不进正文(速览区,通常不调用本 Skill);<50 不进。本 Skill 只写**已进正文**的条目。
3. **写标题**(≤30 字):「谁 + 做了什么 + 对谁有用」。参考句法:「[企业/品牌][产品]上线[新能力],[服务对象]可[效果]」。
4. **写一句话要点**(≤40 字):一句话说清核心事实,供不熟悉 AI 的同事秒懂。
5. **写正文 2-3 段**(200-400 字):
   - 首段给结论(首句结论规则):谁 + 何时 + 做了什么 + 核心影响,禁止「近日 / 据悉 / 据媒体」等铺垫开头。
   - 中段拆工作流:原流程 → AI 介入点(workflow_stage / ai_capabilities)→ 新流程;判数据闭环是否成立(输出是否回流影响下一轮教学)。
   - 末段写行业含义与局限:定位竞品意义;limitations / verification 中的存疑点如实写出(官方宣传 vs 实测差异)。
6. **写桃李含义**(1-2 句)+ **借鉴分级**:落定四类之一,不可模糊;「可直接借鉴 / 需自行研发 / 可购买第三方 / 暂不值得投入」。
7. **标来源**:列出本条目实际引用的来源(S 级优先,标 `S/A/B/C` + source_url);存疑处注明进入附注区。
8. **自检**:标题 ≤30 字、条要点 ≤40 字、正文 200-400 字(2-3 段)、核心事实有 S 级来源、全文以「桃李」称呼公司、无推广腔、无自动发布表述。全部通过后交付。

## 五、写作规范

### 5.1 硬性约束(不可违反)

- **每条核心事实 ≥1 个 S 级来源**(见主文档「信息源分级」);仅有 B 级线索的条目必须先回源核查后再写,核查未完成不得定稿。
- **篇幅 200-400 字**(正文 2-3 段,不含桃李含义段);标题 ≤30 字;条要点 ≤40 字。
- **企业自述(S 级)与实际案例(A 级)必须区分表述**,不得混写;官方宣传与第三方实测不一致处必须如实写出。
- **评分不进正文**:scoring 的分数、档位、理由不得作为正文字句输出(它们只决定条目位置,见步骤 2)。
- 只写输入信号能支撑的事实,不凭空新增;new_change 必须体现在正文(「本次新变化」是核心)。

### 5.2 语言规范(面向公司全员,非技术读者)

- 全文以「桃李」称呼公司;句子 ≤40 字;不堆叠英文缩写。
- 首句直接给结论;禁止以「近日、据悉、据媒体」等铺垫开头。
- 术语按 C 分册替换表替换(首批):Agent → AI 智能体;多模态 → 能读图、能听音;OCR → 文字识别;工作流 → 做事流程;数据闭环 → AI 结果反哺下一轮教学;上下文长度 → 一次能读入的信息量;私有化部署 → 数据装在自己服务器上;大模型 → AI 大模型(首次全称,之后简称「AI」)。无法替换的术语首次出现给一句括号解释。
- 标题不用修辞、不堆成语、不用感叹号;正文无推广腔、无「引领 / 颠覆 / 赋能」式宣传词。

### 5.3 正文三段式(场景 → 变化 → 数据闭环)

- 首段:核心事实 = 场景 + 谁 + 做了什么。
- 中段:工作流变化 = 原流程 → AI 介入后流程;数据闭环 = 输出是否回流。
- 末段:行业含义 + 局限 / 存疑(引用 limitations / verification)。

### 5.4 桃李含义与借鉴分级

- 桃李含义 1-2 句,指向具体可借鉴 / 验证 / 接入的动作(呼应主文档「企业 AI 工作流拆解模板」第 9 步)。
- 借鉴分级必须落定四类之一,不可模糊:
  1. **可直接借鉴** — 已有成熟做法,桃李可照搬或轻量改造;
  2. **需自行研发** — 核心价值需自建,不依赖外部;
  3. **可购买第三方** — 存在成熟可采购的产品 / 服务,成本低于自研;
  4. **暂不值得投入** — 观望即可,同时给出重新评估的触发条件。

## 六、示例(构造,非本期真实数据)

> 输入为 A 分册示例信号 SIG-2026-W33-0001(构造):好未来 / 学而思 / 小思 AI 1对1,`source_level=S`,`scoring.total=79`。

**C-B01 学而思小思 AI 1对1 上线作文批改 AI 智能体,写入学情报告**

- **一句话要点**:AI 逐句诊断作文并给改写建议,结果回流学情报告,把批改做成闭环。
- **企业/产品**:好未来 / 学而思 / 小思 AI 1对1
- **教育场景**:个性化学习-写作批改
- **工作流变化**:原流程「学生写作 → 教师批改 → 学生改错」→ 新流程「AI 逐句诊断 → 生成改写建议 → 教师审核 → 结果写入学情报告 → 下一轮练习规划」
- **数据闭环**:是。批改结果与错因写入学情报告,驱动下一轮练习规划。
- **来源等级**:S(官方发布页)+ A(官方公众号教师端审核演示)
- **桃李含义**:语文批改场景可试点同款 AI 智能体工作流;逐句诊断与改写生成能力可先行验证是否外采第三方,归因逻辑需自研。
- **借鉴分级**:可直接借鉴(流程骨架)+ 需自行研发(错因归因)+ 可购买第三方(改写生成)。

**正文(2 段,示例):**

小思 AI 1对1 本周上线作文批改 AI 智能体,学生提交作文后自动做逐句诊断并给出改写建议,把原本靠教师逐篇批改的环节交给 AI 完成。批改结果连同错因一起写入学情报告,用于规划下一轮练习。

对桃李而言,语文写作批改是高度相近的场景。该闭环把「批改—归因—改写建议—学情回流」串成一段流程,其中改写生成已有成熟第三方能力可购买,错因归因依赖学科数据积累需自行研发。建议教研组以 2-4 周小范围试点「AI 预批改 + 教师审核」,用教师采纳率与返改率验证后再决定是否扩大。

**桃李含义**:详见上段;试点数据作为「是否立项」判据。

**来源标注**:来源 1(官方产品页,S)、来源 2(官方公众号教师端演示,A)。官方宣传与第三方实测差异已记录,详见附注区。
